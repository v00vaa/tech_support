# Клиентская аутентификация и личный кабинет

## Разделение учётных записей

Сотрудники и клиенты используют одну Flask-Login session infrastructure, но разные типы identity:

- `employee:<id>` — сотрудник;
- `client:<id>` — клиент.

Новые сессии используют префиксы, поскольку числовые первичные ключи в таблицах `employees` и `clients` могут совпадать. Для обратной совместимости числовой ID в ранее созданной сессии трактуется только как ID сотрудника; клиентские сессии всегда используют префикс `client:`.

`load_user` проверяет тип identity, существование записи и активность аккаунта. Клиент без пароля не может войти. Деактивированный аккаунт не загружается из сессии.

## Маршруты клиента

| Маршрут | Назначение |
| --- | --- |
| `GET/POST /client/login` | Вход по логину и паролю |
| `POST /logout` | Выход из клиентской или сотруднической сессии |
| `GET /portal/` | Список собственных обращений |
| `GET/POST /portal/dialogs/new` | Создание обращения и первого сообщения |
| `GET/POST /portal/dialogs/<id>` | Просмотр и ответ в собственном обращении |

Регистрация остаётся на `/register`; после неё клиент может войти на `/client/login`.

## Контроль доступа

- Клиентские запросы к маршрутам сотрудников, API и настройкам блокируются на уровне `before_request`.
- Сотрудник не может использовать клиентский портал: портал проверяет тип пользователя отдельно.
- Список обращений выбирается по `Dialog.client_id = current_user.id`.
- Карточка обращения также запрашивается одновременно по ID и ID текущего клиента; перебор ID не раскрывает чужие обращения.
- В клиентском интерфейсе выводятся только публичные сообщения. Внутренние заметки сотрудников не отображаются.
- Клиентская форма ответа не содержит поля `is_internal`; сервер принудительно записывает `is_internal=False` и `author_type=CLIENT`.
- Клиент не может продолжить закрытое обращение.

## Пароли и сессии

Пароли хранятся только в виде хеша через Werkzeug. Минимальная длина пароля при регистрации — 12 символов. Логин сравнивается без учёта регистра. При деактивации клиента существующая сессия перестаёт проходить загрузку пользователя.

## Миграция

Миграция `20261114_02_client_active` добавляет `clients.is_active` с безопасным значением по умолчанию `TRUE`. Её нужно применить после предыдущих миграций командой:

```powershell
docker compose run --rm migrate
```

Перед применением на рабочей базе необходимо сделать резервную копию и проверить текущую ревизию Alembic.


## Ограничение попыток входа

- Клиентский вход: не более 5 запросов в минуту с одного IP-адреса.
- Запрос восстановления: не более 3 запросов в час с одного IP-адреса.
- Проверка токена восстановления: не более 10 запросов в час с одного IP-адреса.
- В production лимиты хранятся в Redis, чтобы быть общими для нескольких Gunicorn workers и экземпляров приложения. Локальное хранилище в памяти допустимо только для разработки и тестов.

## Восстановление пароля

Маршруты:

- `GET/POST /client/password-reset` — запрос письма восстановления;
- `GET/POST /client/password-reset/<token>` — установка нового пароля.

Ответ на запрос восстановления одинаков независимо от того, существует ли email. Токен подписан ключом приложения, действует 30 минут по умолчанию и привязан к текущему хешу пароля: после смены пароля он становится недействительным. В БД токен не сохраняется. После успешной смены пароля пользователь возвращается на страницу входа.

Для отправки писем задайте SMTP-параметры через переменные окружения:

- `SUPPORT_SMTP_HOST`, `SUPPORT_SMTP_PORT`;
- `SUPPORT_SMTP_USERNAME`, `SUPPORT_SMTP_PASSWORD`;
- `SUPPORT_SMTP_SENDER`, `SUPPORT_SMTP_USE_TLS`;
- `SUPPORT_PUBLIC_BASE_URL` — внешний HTTPS-адрес приложения в production.

В production также требуется `SUPPORT_RATE_LIMIT_STORAGE_URI=redis://...` или `rediss://...`. Для локального Docker Compose Redis подключён автоматически; SMTP нужно настроить отдельно. Пока SMTP не настроен, запрос восстановления показывает безопасный общий ответ, но письмо отправить невозможно.
