# Roadmap проекта Support Desk

Ветка: `feature/frontend-auth-dashboard`

Документ фиксирует план исправления текущего прототипа и последующей разработки. Отметки выполнения ставятся только после внесения изменений и проверки результата.

## Целевой процесс обработки обращений

1. Клиент создаёт обращение из личного кабинета.
2. Новое обращение автоматически попадает в очередь единственной активной роли, выбранной администратором как первый уровень поддержки.
3. Сотрудник, состоящий в этой роли, может атомарно взять обращение. Одно обращение не могут одновременно получить два сотрудника.
4. Сотрудник может передать обращение только в роль, разрешённую существующей конфигурацией маршрутизации.
5. После передачи обращение снимается с текущего сотрудника и появляется в очереди целевой роли.
6. Сотрудники не создают обращения от имени клиентов через рабочее место. Ручное создание аккаунта клиента остаётся отдельным сценарием для систем без интеграции с корпоративной БД.

## Этап 1. Привести создание обращений к целевому процессу

- [ ] Удалить создание обращений из интерфейса рабочего места сотрудника.
- [ ] Удалить или закрыть соответствующий маршрут создания обращения сотрудником и убрать неиспользуемые формы/шаблоны/разрешения, если они больше нигде не нужны.
- [ ] При создании обращения клиентом находить выбранную администратором роль первого уровня.
- [ ] Назначать новую заявку в очередь этой роли, задавать время постановки в очередь.
- [ ] Сохранять обращение, первое сообщение и вложения как согласованную операцию; при ошибке откатывать БД и удалять уже записанные файлы.
- [ ] Добавить понятную обработку ситуации, когда активная роль первого уровня ещё не настроена.

## Этап 2. Настройка первого уровня поддержки

- [ ] Добавить к основной роли признак выбора в качестве первого уровня поддержки.
- [ ] Добавить в список ролей административный checkbox «Первый уровень».
- [ ] При выборе одной роли автоматически снимать выбор с остальных; не разрешать выбирать неактивную или специальную роль.
- [ ] Ограничить изменение настройки администраторами и защитить POST CSRF.
- [ ] Обеспечить целостность выбора на уровне БД и миграции; корректно обработать существующую системную роль первого уровня при миграции.
- [ ] Убрать зависимость бизнес-логики от фиксированного кода `support_level_1`; системную роль не считать выбранной автоматически без явной настройки.

## Этап 3. Исправить маршрутизацию между ролями

- [ ] Сохранить существующий интерфейс настройки входящих и исходящих маршрутов.
- [ ] Разрешать передачу только по явно настроенному маршруту от текущей роли к целевой.
- [ ] Проверять, что сотрудник состоит в текущей роли обращения и имеет право на передачу.
- [ ] При передаче очищать ответственного сотрудника, менять очередь и время постановки в очередь, возвращать обращение в статус ожидания очереди.
- [ ] Записывать системное событие о передаче в той же транзакции, что и изменение обращения.
- [ ] Проверить автоматическую переадресацию по таймеру: она должна соблюдать те же правила маршрутов и оставлять системную запись в истории.

## Этап 4. Очереди и атомарный захват обращения

- [ ] Проверить, что очереди показывают обращения без ответственного сотрудника в статусах ожидания.
- [ ] Проверить атомарность захвата: только один параллельный запрос может назначить ответственного.
- [ ] После захвата переводить обращение в статус «В работе» и сохранять событие назначения.
- [ ] Проверить, что обращение после передачи не исчезает из очереди целевой роли.
- [ ] Проверить счётчики очередей и раздел «Мои обращения» на соответствие фактическому ответственному и роли.

## Этап 5. Доступ и история обращений

- [ ] Проверить разделение клиентских сообщений и внутренних заметок.
- [ ] Убедиться, что клиентские маршруты, списки, история и вложения никогда не раскрывают внутренние заметки и закрытые вложения.
- [ ] Проверить системные события создания, взятия, передачи, смены статуса и назначения.
- [ ] Проверить доступ сотрудников к обращениям с учётом роли, назначения и разрешений.
- [ ] Проверить обработку файлов при ошибках БД и недоступности хранилища.

## Этап 6. Тестирование и качество

- [ ] Добавить/обновить unit-тесты выбора первого уровня и ограничений маршрутов.
- [ ] Добавить тесты создания обращения клиентом с автоматической постановкой в очередь.
- [ ] Добавить тесты запрета создания обращения сотрудником.
- [ ] Добавить тесты успешной и запрещённой передачи между ролями.
- [ ] Добавить конкурентный тест атомарного захвата обращения.
- [ ] Добавить тесты доступа клиента к сообщениям и вложениям.
- [ ] Проверить миграции: одна актуальная head-ревизия, upgrade и downgrade на тестовой БД.
- [ ] Запустить `ruff format --check app tests`, `ruff check app tests`, `mypy app` и `pytest`; исправить найденные регрессии.

## Этап 7. Дальнейшая разработка после стабилизации процесса

- [ ] Довести карточки клиентов и сотрудников: поиск, фильтры, пагинация и отображение связи с корпоративной системой.
- [ ] Реализовать приглашения сотрудников вместо ручной установки паролей.
- [ ] Реализовать интеграции каналов и API создания обращений из внешних систем.
- [ ] Реализовать рабочие процессы и правила автоматической маршрутизации.
- [ ] Реализовать модерацию входящих сообщений и настраиваемые фильтры.
- [ ] Добавить классификацию обращений и AI-помощь с возможностью локального запуска модели.
- [ ] Реализовать уведомления и контроль сроков обработки (SLA).

## Правила ведения roadmap

- Задача отмечается выполненной только после изменения кода и соответствующей проверки.
- Если реализация выявляет необходимость изменить архитектурное решение, сначала фиксируется причина и обновляется этот документ.
- После каждого завершённого этапа указываются фактический результат и оставшиеся ограничения.


## Текущий статус реализации

В текущей серии изменений уже внесён код для следующих пунктов (до запуска проверок они остаются незакрытыми в чек-листах выше):

- Добавлен признак первого уровня поддержки у основной роли, миграция с частичным уникальным индексом и административный checkbox непосредственно в списке ролей.
- Для существующих установок миграция сохраняет роль `support_level_1` как первоначальный выбор, если она уже существует и активна. В новых установках выбор выполняется администратором после bootstrap.
- Клиентское создание обращения назначает его выбранной роли первого уровня; при отсутствии настройки возвращается ошибка вместо создания обращения без очереди.
- Удалены маршрут, форма и кнопка создания обращения сотрудником в HTML-интерфейсе; создание через служебный JSON API также запрещено. Редактирование существующих обращений сохранено отдельно и больше не позволяет менять очередь напрямую.
- Передача между ролями требует существующего маршрута и членства сотрудника в исходной роли; передача возвращает обращение в очередь и добавляет системное событие в ту же транзакцию.
- Автоматическая передача также возвращает обращение в очередь и записывает системное событие. Захват обращения и запись события объединены в одну транзакцию.
- Добавлены и обновлены тесты выбора первого уровня, клиентского создания и отказа при ненастроенной очереди, запрета создания сотрудником через HTML и API, захвата обращения и маршрутизации.

**Статус проверки:** автоматические тесты, Ruff, mypy и миграции ещё не запускались на рабочем окружении проекта. Чек-листы этапов будут отмечены после фактического запуска и исправления найденных проблем.


## Дополнение после локальной проверки

По результатам запуска проверок на Windows (Python 3.14.5):

- `pytest`: 129 passed, 1 failed; покрытие 82.88%.
- Единственный тест падал на главной странице: шаблон `index.html` ссылался на удалённый endpoint `dialogs.dialog_create`. Ссылка на создание обращения сотрудником удалена.
- `mypy` находил возможный `None` у `dialog.assigned_role` в построении списка маршрутов. Добавлена явная проверка отсутствующей роли.
- `flask db upgrade` останавливался до подключения к БД, поскольку `migrations/env.py` пытался прочитать отсутствующий необязательный файл `migrations/alembic.ini`. Загрузка logging-конфигурации теперь выполняется только если файл существует.
- Ruff выявил форматирование в семи файлах и один неотсортированный импорт. Эти форматирующие исправления ещё требуется применить локально командой `ruff format app tests`; импорт можно исправить командой `ruff check app tests --fix`.

**Повторная проверка после этих исправлений ещё не выполнена.** Следующая проверка должна включать `flask db upgrade`, `ruff format --check app tests`, `ruff check app tests`, `mypy app` и `pytest`.
